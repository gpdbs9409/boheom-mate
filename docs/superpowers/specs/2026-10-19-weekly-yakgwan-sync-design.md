# 주간 실손 약관 자동 수집·반영 설계

작성일: 2026-10-19 · 기간: 30일(2026-10-19 ~ 2026-11-18)

## 왜 하는가

보험메이트는 운영자가 약관 PDF를 미리 넣어 두는 방식이다(`products.py` 주석). 지금 상담 가능한 상품은 KB 실손 2개뿐이고,
메뉴에는 보험사 9곳이 있지만 나머지 8곳은 "준비 중"이다. 새 약관이 나왔는지 매주 공시실을 돌아보고, 받고, 넣는 일을
사람이 하면 빠뜨리기 쉽고 시간이 든다. 이 일을 매주 자동으로 돌리되, **사이트에 반영하는 순간은 운영자가 Slack에서 승인**한다.

틀린 약관이 들어가면 가입자에게 틀린 근거로 답하게 되므로, "자동으로 많이 넣기"보다 "틀린 걸 넣지 않기"가 우선이다.

## 목표

1. 매주 월요일 오전 9시(KST), 대상 보험사 공시실에서 **실손의료보험** 약관 목록을 읽고 지난 실행 결과와 비교해 새 약관을 찾는다.
2. 새 약관 PDF를 내려받아 `data/`에 저장하고, `ingest.split_articles`로 조항을 나눈다.
3. 나눈 결과를 자동 점검하고, 요약을 Slack에 올린다.
4. 운영자가 그 Slack 메시지에 "승인" 답글을 달면, 임베딩해 `chroma_db/`에 저장하고 상품 목록에 등록해 사이트에서 상담할 수 있게 한다.
5. 30일 단계: 1주차 KB손해보험만 → 2~4주차에 매주 2~3곳씩 추가(삼성화재, 현대해상, DB손해보험, 메리츠화재, 한화손해보험, 롯데손해보험, 흥국화재, NH농협손해보험). 추가 순서는 빌더 재량.

## 하지 않는 것

- 실손 외 보험 종류(암, 운전자, 어린이, 치아)는 확인하지 않는다.
- 조항 나누기 규칙(`find_sections` 등)을 보험사별로 고치는 일은 이 프로젝트 범위가 아니다. 점검에서 걸리면 멈추고 알릴 뿐이다.
- 계산기·용어 사전을 새 약관에 맞추는 일도 범위 밖이다.

## 실패로 보는 경우 (돌아가더라도)

- 운영자 승인 없이 사이트(`chroma_db/`, 상품 목록)가 바뀐다.
- 조항이 잘못 잘린 약관이 점검을 통과해 "정상"으로 보고된다.
- 공시실 화면이 바뀌어 목록을 못 읽었는데 "새 약관 없음"으로 보고된다. 못 읽은 것과 없는 것은 반드시 구분해서 보고한다.
- 같은 약관을 매주 "새 약관"으로 다시 알린다.
- 자동화가 사이트(Streamlit)를 죽이거나 메모리 부족으로 멈추게 한다.

## 제외한 후보와 이유 (브레인스토밍 결과 기록)

- 방문자 질문 분석(`questions.db`): 병력 등 민감한 개인정보가 들어 있을 수 있어 제외.
- 결제 관련: 사이트에 결제 기능이 없음.
- 보험사 계정 로그인이 필요한 자료: 남의 시스템 권한이 필요해 제외. 공시실은 로그인 없는 공개 페이지라 대상이 된다.

## 제약

- **실행 위치: 기존 EC2**(t3.micro, 서울, 메모리 1GB + 스왑 2GB, `/home/ubuntu/boheom-mate`). 새 서버를 만들지 않는다.
  같은 서버의 `chroma_db/`에 직접 쓰므로 로컬→rsync 단계가 없다. SSH는 운영자 집 IP만 허용되어 있어 외부(클라우드)에서 접근하는 방식은 쓸 수 없다.
- 기존 스택을 따른다: Python 3.12, `ingest.py`의 `extract_text` / `split_articles` / `build_index`, OpenAI `text-embedding-3-small`, Chroma 컬렉션 `yakgwan`.
  LangChain 같은 프레임워크를 들이지 않는 프로젝트 방침(README)을 지킨다.
- 공시실에는 사람이 보는 정도의 빈도로만 접근한다(주 1회, 보험사당 몇 번의 요청). `robots.txt`와 이용 조건을 확인한다.
- 비밀값(OpenAI 키, Slack 토큰)은 서버 `.env`에만 두고 git에 넣지 않는다.
- 운영자는 초보 개발자이고 이 앱은 금융권 취업 포트폴리오다(CLAUDE.md). 운영자가 면접에서 설명할 수 있도록 구조를 단순하게 유지한다.
- CLAUDE.md의 기존 결정 "서버에서 ingest 안 함(로컬 → rsync)"은 이 설계로 바뀐다. 구현 시 CLAUDE.md도 함께 고친다.

## 운영자가 정한 것

- 대상: 9개 보험사의 실손의료보험 약관만.
- 범위: PDF 받기부터 사이트 반영까지.
- 조항 나누기 결과가 이상하면 멈추고 운영자에게 확인을 요청한다.
- 결과가 정상이어도 반영 전에 **Slack에서 운영자가 확인한 뒤** 반영한다.
- 알림 채널: Slack(운영자 소유 워크스페이스).
- 실행 시각: 매주 월요일 오전 9시.
- 실행 위치: 기존 EC2.
- 단계적 확대: 1주차 KB만, 이후 매주 2~3곳 추가.
- **"확인 필요"로 걸린 약관도 운영자가 Slack에서 승인할 수 있다.** 점검 규칙을 보험사별로 고치지 않으므로, 다른 보험사 약관은
  대부분 "확인 필요"로 나올 것으로 예상하고 운영자가 보고 판단한다. 이 경우 Slack 메시지에 걸린 이유와 판단에 필요한 정보
  (구역별 조항 수, 조항 번호 목록의 이상 부분, 의심 조항 몇 개의 제목과 첫 줄)를 함께 보여 준다. 승인된 "확인 필요" 건은
  실행 기록에 "점검 경고 있음, 운영자 승인"으로 남긴다. "확인 필요"를 "정상"으로 표시하는 일은 여전히 실패로 본다.
- **새 판이 나오면 옛 판과 같이 둔다.** 실손은 가입 시점 약관이 적용되기 때문이다. 상품 데이터는 판을 구분해 기록하고,
  "내 보험 고르기"에서 판까지 고를 수 있게 한다(기본 선택은 최신 판). Chroma에서 옛 판 조각을 지우지 않는다.

## 설계자(Claude)가 정한 것 — 운영자 확인 필요

- **승인 방식: Slack 메시지에 "승인" 답글.** 서버가 몇 분 간격으로 해당 스레드 답글을 확인해 반영한다. Slack 버튼(interactivity)은
  서버에 Slack용 공개 주소를 새로 열어야 해서 쓰지 않는다. 약관 여러 건이 한 주에 나오면 약관마다 메시지를 따로 올려 건별로 승인한다.
  "보류"나 다른 답글은 반영하지 않으며, 승인되지 않은 건은 다음 주 요약에 "승인 대기"로 다시 표시한다.
- **"이상해 보임" 기준(점검 항목)** — 하나라도 걸리면 "확인 필요"로 보고:
  - 텍스트를 추출하지 못함(스캔 PDF 등)
  - 보통약관 구역을 찾지 못함, 또는 모든 조항이 한 구역으로 몰림
  - 같은 구역 안에서 조항 번호가 빠지거나 겹치거나 순서가 뒤집힘
  - 조항 수가 너무 적음(기준값은 빌더가 KB 약관 5개를 보고 정함)
  "정상"이든 "확인 필요"든 운영자 승인 전까지는 반영하지 않는다.
- **공개 사이트의 "약관 넣기" 탭 숨기기.** 지금은 방문자 누구나 "저장하기"를 눌러 OpenAI 비용을 쓰게 하거나 DB를 바꿀 수 있다.
  약관 넣기가 서버 작업으로 옮겨가므로 배포판에서는 이 탭을 보이지 않게 한다(로컬 개발에서는 계속 쓸 수 있게 하는 방법은 빌더 재량).
- **상품 목록을 코드 밖으로.** 지금 `products.py`의 `PRODUCTS`는 코드라서 자동화가 고치려면 파일 수정 + 앱 재시작이 필요하다.
  자동화가 쓰고 앱이 읽는 데이터 파일(예: JSON)로 옮기는 것을 권한다. 형태는 빌더 재량.
- **"새 약관" 판정 기준:** 상품명 + 판(예: `26.09`)이 지난 기록에 없으면 새 약관. 기존 상품의 개정판도 새 약관으로 본다.
  지난 실행 기록은 서버 파일로 남긴다.
- **첫 실행:** KB의 기존 5개 PDF(`data/`)와 DB에 있는 2개는 이미 알고 있는 것으로 기록에 미리 넣어, 첫 주에 다시 알리지 않는다.
  새 보험사를 추가하는 주에는 그 보험사의 현재 실손 약관이 모두 "새 약관"으로 나오며, 이는 예상된 동작이다.
- **KB의 받아만 둔 3개(계약전환용, 다이렉트, 다이렉트간편):** "이미 아는 약관"으로만 기록하지 않고, 1주차에 "승인 대기"로 Slack에 올린다.
  전체 흐름의 첫 실전 시험이 된다. 계약전환용 파일 이름에는 판이 없으므로 기록에는 `26.09`로 적는다(`products.py` 상품명 기준).
  DB의 간편가입 162조각(예전 방식 분할)을 다시 처리하는 일은 범위 밖이다.
- **"현재 실손 약관"의 범위:** 공시실에서 **판매 중인 상품의 최신 판**만 본다. 판매 중지 상품과 과거 판은 제외한다.
  실손으로 보는 상품: 기본형, 간편가입(유병력자), 노후, 계약전환용, 다이렉트 계열. 단체 실손과 다른 보험에 붙은 실손 특약은 제외한다.
  공시실이 판매 중과 판매 중지를 구분하지 않으면 그 보험사는 보고서에 그 사실을 적고 최신 판만 고른다.
- **자동으로 읽을 수 없는 공시실:** `robots.txt`나 이용 조건이 자동 접근을 막거나, 헤드리스 브라우저 없이는 목록을 읽을 수 없으면
  그 보험사는 자동 확인을 하지 않고 주간 요약에 "자동 확인 불가"로 계속 표시한다. 대신 운영자가 PDF를 직접 받아 정해진 폴더에 넣으면
  같은 점검 → Slack 승인 흐름을 타게 한다(수동 입력 경로). t3.micro에 Chromium/Playwright는 올리지 않는다.
  따라서 8개 보험사 추가는 확정 약속이 아니라 최선 목표다.
- **배포와 데이터 소유:** 이 설계 이후 `chroma_db/`, `data/`, 상품 데이터 파일, 실행 기록은 **서버가 원본**이다.
  코드를 서버에 올릴 때 이 경로들을 덮어쓰지 않게 배포 절차를 바꾸고(rsync 제외 목록 등), CLAUDE.md의 "로컬 `chroma_db/`를 rsync로 올린다"를 고친다.
  로컬 개발에 최신 데이터가 필요하면 서버에서 내려받는다.

## 매주 남는 것

- `data/`의 새 PDF 파일
- Slack 주간 요약 1건: 보험사별 "새 약관 n건 / 없음 / 목록 읽기 실패"
- Slack 약관별 메시지: 상품명, 판, 조항 수, 구역별 조항 수, 점검 결과(정상 / 확인 필요 + 이유), 승인 방법 안내
- 승인 후 Slack 답글: "반영 완료, DB 전체 n조각" 또는 실패 이유
- 서버 실행 기록 파일(언제 무엇을 확인했고 무엇을 받았는지)

## 빌더에게 맡기는 것

- 보험사별 공시실 목록 읽는 방법(HTML 파싱, 공개 JSON 등)과 보험사 추가 순서
- 스케줄 방식(cron, systemd timer 등)과 승인 확인 주기
- Slack 앱 구성과 권한 범위(메시지 쓰기, 스레드 답글 읽기에 필요한 최소 권한)
- 사이트가 돌아가는 중에 `chroma_db/`에 쓰는 방법(동시 접근 문제, 반영 후 앱이 새 데이터를 읽게 하는 방법)
- t3.micro 메모리 안에서 사이트와 함께 돌아가도록 하는 방법
- 점검 기준값
